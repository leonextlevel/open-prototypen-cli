# Audit

Prefer a separate agent context from the designer. Read product definition, flows, screen map, visual research, design direction, `design/system.md`, `design/system.yaml`, rendered screens, and the `Design System` page exported with `open-prototypen render --system`. Use `open-prototypen inspect canvas --json`, `inspect system --json`, and `validate canvas --json` for geometry and native structure. Run OpenPencil lint and the relevant color, typography, spacing, and overlap analyses when available, knowing their limits: `color-contrast` skips text bound to a variable, ignores the lower large-text threshold, and only compares against ancestors' fills, and `touch-target-size` matches layer names against a 44 px goal rather than WCAG's 24 px minimum, as [the accessibility reference](../open-prototypen-design/references/accessibility.md) explains. Rely on `validate canvas` instead: `text-contrast` checks text in screens and masters, including bound fills, against the WCAG thresholds, and `text-contrast-unchecked` counts text whose background it could not determine, which you review in the renders; inspect the actual PNGs rather than treating warnings as an aesthetic score.

Examine clarity, hierarchy, UX, accessibility, coherence, and design consistency. Review the renders with [the design review questions](../open-prototypen-design/references/review.md), including the intentionality pass, genericity, and cross-screen consistency; record product fit and genericity, and consistency across screens, in the report's optional sections. Judge intentionality with the questions in [intentional design](../open-prototypen-design/references/intentional-design.md) and the native system against [the design system reference](../open-prototypen-design/references/design-system.md) rather than restating their guidance. Check that every state in the flows, including errors, conflicts, and deadlines, is reachable in the prototype, treating `unreachable-screen` warnings from `validate canvas` as findings. Check that the `contrast` list in `system.yaml` covers the pairs the screens use and treat `contrast-pair` and `small-target` warnings as accessibility findings, or record them as accepted exceptions when an inline, equivalent, or essential exception of WCAG 2.5.8 applies. Reaching an error state is not enough: open the compiled prototype in `prototype/dist`, trigger every error, conflict, and deadline state, and follow its recovery. Fill the `Error Recovery` table with the trigger, the recovery action, the next screen or state, and whether the task can still be completed. A recovery screen that only offers going back, while the flows expect the user to finish another way, is a finding. Walk every demonstrable rule in the screen map's `Rule Coverage` table in the compiled prototype and report a rule whose expected result does not appear; require a reason for each rule marked information only. Check that referenced token roles are visibly coherent, declared components appear as linked instances, `component-screen-undeclared` and `component-unused` warnings are resolved or recorded as exceptions, interface icons are editable vectors with consistent alignment and weight, and represented states match the flows. Ground every finding in a screen, artifact, or inspected node. Distinguish defects from intentional, documented exceptions in `design/system.md`. Do not revise requirements to defend the prototype. Write `audit-report` using its CLI instructions and validate it. If the reviewing context cannot write files, it returns the complete Markdown report instead; the calling agent writes it verbatim to the artifact path, runs `open-prototypen validate audit-report`, and notes in `Summary` that the write was delegated. The caller does not edit findings; a validation failure goes back to the reviewer. The auditor records findings; the designer, component reviewer, or refiner makes changes.
