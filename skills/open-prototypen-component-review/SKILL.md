# Component review

Use a separate agent context after the first screen assembly and before accepting the prototype. Run it in a context that can edit the `.fig`; when it cannot, the reviewer returns an ordered list of changes, each naming the node, the change, and the reason, and the calling agent applies them in order, then runs `validate canvas --json` and returns the result to the reviewer for confirmation. Read the screen map, product flows, `design/system.md`, `design/system.yaml`, and the `Design System` page in the `.fig`, exported with `open-prototypen render --system`. Inspect every page with `open-prototypen inspect canvas --json`, the native structure with `inspect system --json`, and the rendered screens. Compare the declared component states with the native masters on `Design System` and their linked instances in screen frames. Look for repeated groups or controls that visually reproduce a master but are detached, and for reusable patterns missing from the inventory. A matching name or appearance alone does not prove an instance is linked. In `inspect system --json`, a linked instance has type `INSTANCE` and a `componentId` naming its master; a detached copy is usually a `FRAME` or `GROUP` with an empty `componentId`, often beside linked siblings of the same master. `validate canvas` only requires one linked instance per declared screen, so it cannot find a copy that sits next to linked instances. It warns `component-screen-undeclared` when a component's instance, direct or nested, sits on a screen its `screens` list omits, and `component-unused` when a master has no linked instance anywhere. Resolve each one: add the screen to the contract, replace the instance, or remove the master; record an intentional case, such as a state no flow shows yet, as an exception.

Correct the `.fig` and artifacts when needed: move missing masters and states to `Design System`, replace detached copies with linked instances, and add genuinely reusable components to `system.yaml` and the page before placing their instances. Remove text on `Design System` that repeats a master's name, reported as `master-label` warnings; keep group headings and token sample labels. Preserve screen content, represented states, and action-node behavior. Replacing nodes renumbers node IDs across the whole document; references survive, but a replacement node has none, so move the old node's reference to the new instance with `open-prototypen ref set <new-id>=<ref>` after clearing or deleting the old node, then confirm with `open-prototypen ref list --json` and `inspect screen <screen> --json`. Read [the headless OpenPencil reference](../open-prototypen-design/references/openpencil-headless.md) before scripting replacements; `detachInstance()` does not exist. Do not make a component for a composition whose specific content or behavior will not be reused. Record each such exception and its reason under `## One-off Compositions` in `design/system.md`, and summarize each review (detached copies found, replacements, and new components) under `## Component Review` there, so later reviews can distinguish intention from drift.

After changes, run `open-prototypen inspect system --json` and `validate canvas --json`, render the affected screens and `render --system`, inspect their PNGs, and rebuild with `open-prototypen prototype`. Resolve validation failures and visual regressions before handing the prototype back. This review checks component use through agent judgment; the CLI's structural validation remains the compilation gate.
